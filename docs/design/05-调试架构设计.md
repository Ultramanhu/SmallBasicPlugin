# 05 调试架构设计

目标：两端 IDE 一致的调试体验——**断点、单步（逐语句/步入/步出）、暂停、继续、变量查看、调用栈、程序终止**。

> **2026-09-26 实施状态**
>
> - **VS Code**：双后端调试均已落地。JS 后端为内嵌调试器（`packages/smallbasic-vscode/src/debug/`，进程内驱动 TS `ExecutionEngine`）；C# 后端为 `SmallBasic.RunHost.exe debug`（原生 DAP over stdio，驱动 .NET `SmallBasicEngine` 的 `NextLine` 模式，见 `visual_studio_plugin/src/SmallBasic.RunHost/Debug/`）。launch.json 以 `backend: javascript | csharp` 选择，两者断点吸附/单步/变量/输入桥接语义对齐（C# 端断点吸附依赖 vendor 编译器新增的 `SmallBasicCompilation.GetExecutableLines()`）。Windows C# 宿主还可调试图形程序。
> - **Visual Studio 2022/2026**：双后端均经 Debug Adapter Host 接入。F5/F10/F11 默认启动随 VSIX 分发的纯 C# DAP；Tools 菜单另有 C#/JS 运行与调试的四个显式入口。JS 路径只分发 bundle，使用外部 Node.js 20+，并在启动前拒绝图形程序。命令过滤器在调试会话激活期间（Break/Run 模式）把 F5/F10/F11 全部转发给调试器。
> - **图形程序调试**：无论 TS 还是 .NET 后端，后续都应先补 `GraphicsWindow/Shapes/Controls/Turtle` 图形宿主，再开放图形程序调试；当前实现中应显式返回 capability 错误，而不是继续执行到运行时崩溃。

## 1. 为什么是 DAP

| 选项 | 评估 |
|---|---|
| **DAP 调试适配器** | VS Code 原生支持；VS 2026 经内置 **Debug Adapter Host** 支持。一套协议两端通吃，UI 全部复用 IDE 标准调试界面 |
| VS AD7 自研调试引擎 | 接口数十个、注册表/COM 集成复杂，工作量约为 DAP 方案的 10 倍，否决 |
| 自绘调试 UI | 两端的旧版在线编辑器即此模式（Monaco 行高亮 + 自绘变量面板），现代 IDE 插件无必要，否决 |

协议统一、引擎双实现：

```
VS Code ──DAP──> sb-debug (TS)              ──> ExecutionEngine (TS)     ← 默认（backend=ts）
        ──DAP──> SB.DebugAdapter.exe (.NET) ──> SmallBasicEngine (.NET)  ← 可选（backend=dotnet）
VS 2026 ──DAP──> SB.DebugAdapter.exe (.NET) ──> SmallBasicEngine (.NET)  ← 默认（经 Debug Adapter Host）
        ──DAP──> node sb-debug.js (TS)      ──> ExecutionEngine (TS)     ← 可选（backend=node）
```

两端 IDE 通过配置项选择调试/运行后端（ADR-5），两个适配器 DAP 语义字段级对齐（见 §5），IDE 调试 UI 完全一致；语言智能不受选择影响，始终用 IDE 原生引擎。

## 2. 引擎调试能力现状与断点补齐

两个引擎均**无断点**，但都有**行级暂停钩子**：

| 引擎 | 暂停机制 | 状态快照 |
|---|---|---|
| TS `ExecutionEngine` | `execute(ExecutionMode.NextStatement)`：指令 `sourceRange.start.line` 变化即置 `Paused` 返回 | `executionStack`（帧栈）+ 指令 `sourceRange`、`memory`（全局变量） |
| .NET `SmallBasicEngine` | `Mode=NextLine`：行变化即 `Pause()`（`SmallBasicEngine.cs:112-119`）；`Mode=Debug` 不自动停 | `GetSnapshot()` → `{ CurrentSourceLine, ExecutionStack, Memory }` |

**断点实现（适配器层，零引擎修改）**：适配器运行循环统一为"逐段推进 + 命中判定"：

```
loop:
    engine.execute(NextLine/NextStatement)     // 推进到下一个源码行边界
    line := 当前行（栈顶帧指令 sourceRange 或 engine.CurrentSourceLine）
    if stepping 或 line ∈ breakpoints[file]:   // O(1) 集合查找
        上报 DAP stopped (reason: breakpoint | step)
        等待 DAP continue/next/stepIn/stepOut 请求
    else if engine.State == Terminated:
        上报 terminated；退出
```

- 每次循环只执行到行边界即返回，断点判定开销 O(1)；SB 程序规模下逐行推进的额外开销可忽略（解释器本身为纳秒~微秒级/指令）。
- **步入/步出**：SB 仅有子程序调用（无嵌套定义）。`stepIn`=NextLine 即自然步入；`stepOut`=记录当前栈深，循环推进直到栈深 < 记录值后暂停；`next`=栈深 ≤ 当前值时在行边界暂停。
- **断点校验**（`setBreakpoints` 响应）：把断点行映射到最近的可执行语句行——用 `Compilation` 的 AST/指令 `sourceRange` 集合做"行 → 最近 ≥ 该行的可执行行"吸附，并返回 `verified: true/false`（空行/注释行 verified=false）。
- **输入阻塞**：`BlockedOnInput/BlockedOnStringInput` 期间适配器不视为 stopped；输入到达后 `InputReceived()` 继续循环。
- **暂停请求**（`pause`）：TS 引擎同步循环需让出事件循环——适配器以 `setImmediate` 分段驱动（每段推进至多 N 行或 5ms），段间检查 pending 的 pause 请求；.NET 引擎直接 `engine.Pause()`。

**可选上游补丁（二期优化）**：在两个引擎各加一个 `ShouldPause(line): boolean` 委托，由引擎内部在行边界回调，免除适配器外层循环。非必需，MVP 不做。

## 3. TS 调试适配器（`packages/sb-debug`）

技术栈：`vscode-debugadapter` npm 包（`DebugSession` 基类）+ `vscode-debuglogger`。

```ts
class SBDebugSession extends DebugSession {
  // DAP 请求映射
  protected initializeRequest(...)        // capabilities: supportsConfigurationDoneRequest 等
  protected setBreakPointsRequest(...)    // 校验+吸附，存 breakpoints[file]
  protected configurationDoneRequest(...) // 标记就绪，launch 后可起跑
  protected launchRequest(...)            // new Compilation(fs.readFileSync(program)) → 诊断检查
                                          // → new ExecutionEngine(compilation)，注入终端 I/O 插件
                                          // → 启动 §2 运行循环
  protected threadsRequest(...)           // 单线程模型：固定 thread id=1
  protected stackTraceRequest(...)        // engine.executionStack 帧 + 指令 sourceRange → StackFrame
  protected scopesRequest(...)            // 单个作用域 "Variables"
  protected variablesRequest(...)         // engine.memory.values 展平（数组递归展开为子变量）
  protected continueRequest(...)          // stepping=false，推进循环
  protected nextRequest() / stepInRequest() / stepOutRequest()  // 见 §2 语义
  protected pauseRequest(...)             // 分段循环检查点置位
  protected disconnectRequest(...)        // engine.terminate()；关终端
  protected evaluateRequest(...)          // MVP：仅支持变量名求值（repl 二期）
}
```

**变量呈现**：`engine.memory`（`ArrayValue`，键值字典）→ DAP `Variable[]`；SB 数组是字典结构，递归展开（`arr["x"][1]` 两级），`variablesReference` 惰性加载。标量显示 `value.ToString()` 与类型（Number/String/Array）。

**I/O 通道**：`console: integratedTerminal`（默认）时 TextWindow 读写经 PTY；`internalConsole` 时走 DAP `output` 事件 + `runInTerminal` 反向请求。**默认集成终端**（Read/ReadNumber 需要真实输入流）。

launch.json 属性：`program`（必填，默认 `${file}`）、`stopOnEntry`（默认 false）、`console`、`trace`。

## 4. .NET 调试适配器（`SB.DebugAdapter`）

技术栈：net8.0 控制台，`StreamJsonRpc` 手写 DAP 帧（Content-Length 头 + JSON），或引用社区 `netduma-libs/DAP` 类库；消息模型与 TS 版字段级对齐（同一 launch.json schema）。

```
Program.cs:
  stdin/stdout DAP 帧循环 → DebugSession 类（请求分发）
  LaunchHandler:  SmallBasicCompilation(File.ReadAllText(program))
                  → 诊断有 error → 回 error response + terminate
                  → new SmallBasicEngine(compilation, new ConsoleLibraries(bridgeChannel))
                  → Mode = NextLine → 运行循环（§2）
```

**I/O 桥接**：调试进程独占 stdin/stdout 给 DAP，因此 `TextWindow` 输入输出**不能**直接用控制台——`ConsoleLibraries` 通过一个**与 VS 通信的辅助通道**（命名管道或经 DAP `runInTerminal` 反向请求让程序跑在 VS 启动的终端里）。MVP 决策：适配器通过 DAP `runInTerminal` 请求让 VS 在集成终端启动 `SB.RunHost debug --pipe <name>`，适配器经命名管道与其桥接 TextWindow I/O；非 UI 库（Math/Array…）在适配器进程内实现。此结构同时被"非调试运行"复用（见 04 §5/6）。

**Debug Adapter Host 注册**：VSIX 提供
- `*.vsdconfig` / JSON 形式的 adapter 声明（`Microsoft.VisualStudio.Debugger.VSCodeDebuggerHost` 识别），指定 adapter exe 路径、`smallbasic` 调试器类型、支持的请求子集；
- `.sb` 文件调试启动模板（F5 时生成默认 launch 配置）。

**Spike 验证清单**（M1 完成，见 08）：Debug Adapter Host 对 `setBreakpoints/launch/stackTrace/variables/continue/next/pause/terminate/runInTerminal` 九个请求的兼容性逐一验证；若 `runInTerminal` 不受支持，降级为命名管道直连 `SB.RunHost` 控制台窗口（conhost 分配）。

## 5. 两端调试语义对齐

| 语义 | 定义（两端一致） |
|---|---|
| 断点吸附 | 断点落在非可执行行 → 最近下一可执行行；`verified` 如实返回 |
| stepIn | 行边界暂停（自然进入子程序） |
| next | 栈深 ≤ 进入时栈深 的行边界暂停 |
| stepOut | 栈深 < 进入时栈深 时暂停 |
| 变量 | 全局变量字典全量展开；数组递归；暂停时刷新 |
| 调用栈 | 子程序帧，帧名=Sub 名，行号=指令 sourceRange |
| 异常 | 引擎 `exception`/诊断 → DAP `stopped(reason: "exception")` + 消息 |
| 终止 | 程序结束/用户停止 → `terminated` + `exited` |

对齐保障：`conformance/debug/` 下的调试场景脚本（断点命中序列、单步序列、变量期望值）以文本 DSL 描述，两端适配器测试各自执行并比对（见 07）。

## 6. 性能与安全

- 逐行推进循环仅在调试会话内启用；非调试运行走 `RunToEnd`，无开销。
- 分段驱动（TS 5ms/段）保证扩展宿主 UI 不冻结。
- 适配器不执行任何引擎外的代码；`File/Network` 等库在调试宿主中默认按 06 文档安全策略启用。
